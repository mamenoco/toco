## 2. APIの基礎知識

ここが今回いちばん不安な部分と伺ったので、丁寧に書きます。

### 2-1. APIとは何か

**APIは「機械用の窓口」です。**

楽天の商品ページを人が見るときは、ブラウザで開いて目で読みます。
これをプログラムにやらせようとすると、見た目のHTMLから商品名を探す羽目になり、
デザインが変わるたびに壊れます。

そこで各社は「プログラム向けの入口」を別に用意しています。
決まった住所（URL）に「うさぎ ケージで検索して」と送ると、
人向けの飾りを一切含まない、整理されたデータが返ってきます。

```
アプリが送る：
  https://app.rakuten.co.jp/services/api/IchibaItem/Search/20220601
    ?applicationId=（あなたの鍵）&keyword=うさぎ ケージ&hits=30

楽天が返す（JSONという形式）：
  { "Items": [
      { "itemName": "三晃商会 イージーホーム・エボ80 WH",
        "itemUrl": "https://item.rakuten.co.jp/chanet/181266/",
        "mediumImageUrls": [...], "reviewCount": 59, "reviewAverage": "4.36" },
      ... ] }
```

このやり取りが「APIを叩く」です。すでに `server.js` の `rakutenSearch()` が
これをやっています。**新しく覚えることは多くありません。**

### 2-2. 「鍵」の種類

APIは誰でも無制限に使えると困るので、利用者を識別する鍵を配ります。3タイプあります。

| タイプ | 中身 | 例 | 扱い |
|---|---|---|---|
| **ID型** | 発行された文字列をURLに付けるだけ | 楽天 applicationId、Yahoo Client ID | 一番簡単 |
| **ID＋秘密鍵型** | 秘密の値はURLに載せずヘッダーで送る | 楽天 accessKey | やや注意 |
| **署名型** | リクエスト内容から毎回ハッシュを計算して添える | Amazon PA-API | **実装が重い** |

今のアプリは ID＋秘密鍵型（楽天）まで対応済みです。署名型（Amazon）だけが別格に面倒で、
そこが §2-5 の判断につながります。

### 2-3. 使うサービス一覧

| サービス | 用途 | 費用 | 取得の難しさ | 今回使うか |
|---|---|---|---|---|
| 楽天ウェブサービス | 商品名・画像・レビュー数・URL | 無料 | 易（登録するだけ） | **使う（実装済み）** |
| Yahoo!ショッピング | 同上（Yahoo!の商品を出したい場合） | 無料 | 易 | **当面見送り**（§3-7） |
| Amazon PA-API | Amazonの商品名・画像・ASIN | 無料 | **難（売上実績が条件）** | **当面見送り**（§2-5） |
| もしもアフィリエイト | 報酬の発生元。**APIは無い** | 無料 | ― | **使う（リンクの型のみ）** |

### 2-4. 楽天ウェブサービス

- 楽天会員でログインし、アプリを1つ登録すると `applicationId` が発行されます
- 2026年の仕様変更で `accessKey` も必要になりました（既にアプリが対応済み）
- **アフィリエイトIDを一緒に渡すと、返ってくるデータに `affiliateUrl` が含まれます**
  → 楽天だけは、リンク生成をAPIに任せられます
- レビューの**本文は取れません**。件数と平均点までです
- 目安として1秒に1リクエスト程度。アプリ側は既に3秒間隔の制御が入っています

**この記事制作フローでは楽天APIが主力**になります。商品の発見・スペック・画像の
すべてがここから取れるためです。

### 2-5. Amazon PA-API を当面見送る理由

Amazonの商品APIには、他社にはない前提条件があります。

1. Amazonアソシエイトの審査に通る
2. **承認後180日以内に3件の適格販売を発生させる**
3. その後も売上が途切れるとAPIアクセスが停止される

つまり「売れていないとAPIが使えない」構造です。記事0本の今は条件を満たせません。
さらに署名型（§2-2）なので実装も重い。

**判断：フェーズ1では実装しません。**
Amazonへのリンク自体は §2-6 の方法で問題なく作れます。困るのは商品画像だけで、
そこは楽天の画像で代替します（§4-6）。

売上が立ってPA-APIが通ったら、後から差し込めるようモジュールは分けておきます。

### 2-6. もしもアフィリエイト（ここが設計の肝）

**もしもアフィリエイトに公開APIはありません。** これは事実として受け入れます。
ただし、リンクを作るために必要なのはAPIではなく「リンクの型」だけです。

もしもの管理画面で発行されるリンクは、おおむねこういう形をしています。

```
https://af.moshimo.com/af/c/click
  ?a_id=1234567     ← あなたの提携ID（広告主ごとに違う）
  &p_id=170         ← 広告主ID
  &pc_id=185        ← 広告枠ID
  &pl_id=4062       ← 広告ID
  &url=https%3A%2F%2Fwww.amazon.co.jp%2Fdp%2FB01234ABCD   ← 飛ばしたい商品ページ
```

**`url=` 以外は、広告主（Amazon／楽天／Yahoo）ごとに常に同じ値です。**
つまり一度だけリンクを発行してもらえば、あとは `url=` の中身を差し替えるだけで、
何百商品でも自分でリンクを作れます。ポチップが内部でやっているのもこれです。

#### リンクテンプレート方式

アプリの設定画面に、3つの入力欄を置きます。

```
Amazon用リンク  [ もしもで発行したリンクを1本まるごと貼る ]
楽天用リンク    [ 　　　　　　同上　　　　　　　　　　　 ]
Yahoo用リンク   [ 　　　　　　同上　　　　　　　　　　　 ]
```

貼ると、アプリが `url=` の後ろを `{{URL}}` に自動で置き換えて保存します。

```
保存されるテンプレート：
https://af.moshimo.com/af/c/click?a_id=1234567&p_id=170&pc_id=185&pl_id=4062&url={{URL}}

記事に出力するとき：
{{URL}} に商品ページのURLをエンコードして差し込むだけ
```

**この方式の利点**

- APIが無くても完全自動化できる
- もしも側の仕様が変わっても、**新しいリンクを1本貼り直すだけ**で全記事が直る
- パラメータの正確な名前を私が推測する必要がない（貼られた実物から読み取る）
- 将来もしもを離れて Amazonアソシエイト直・楽天アフィリエイト直に変えても、
  テンプレートを差し替えるだけで済む

**確認が必要なこと**：上のパラメータ名は一般的な形ですが、実物と照合して確定させます。
もしもの管理画面から Amazon・楽天 それぞれ1本ずつリンクを発行して、
実装時に見せてください。

### 2-7. 鍵の保管

APIの鍵は、他人に渡ると勝手に使われます。次のように扱います。

| やること | 理由 |
|---|---|
| 鍵は `toco-app/data/` の中だけに置く | Mac のローカル。外に出ない |
| **`data/` は Git に入れない**（`.gitignore`） | GitHubに鍵を上げてしまう事故を防ぐ |
| ビルド出力に鍵を含めない | 公開サイトのHTMLから鍵が読めてはいけない |
| もしものリンクは公開されて問題ない | a_id は元々ブラウザから見える値 |

**「data/ を .gitignore に入れる」はいちばん事故が多いところなので、
リポジトリを作った最初の作業として実施します。**

### 2-8. 呼び出し回数の考え方

APIは「無料だから叩き放題」ではありません。多く叩くと止められます。

- 一度取った商品情報は**ローカルに保存して使い回す**（商品マスタ・§4-2）
- 定期実行・自動巡回はしない。**ボタンを押したときだけ**動かす
- 連続実行には間隔を空ける（実装済み：3秒）

## 3. ポチップ相当機能の設計

### 3-1. ポチップがやっている5つのこと

| # | 機能 | 新アプリでの扱い |
|---|---|---|
| 1 | 商品をデータベースに登録して使い回す | **商品マスタ**（§3-2） |
| 2 | Amazon/楽天/Yahoo のボタンを並べたカードを出力 | **ビルド時にHTML生成**（§3-3） |
| 3 | アフィリエイトリンクを自動で組み立てる | **リンクテンプレート方式**（§2-6） |
| 4 | 価格を定期取得して自動更新 | **価格を出さない**（§3-7） |
| 5 | どのボタンが押されたか計測 | **GA4イベント**（§3-5） |

4以外はそのまま再現できます。4は方針で回避します。

### 3-2. 商品マスタ

いまは商品データが記事プロジェクトの中に埋まっています（`projects[].products[]`）。
同じ商品を別の記事でも使うため、**独立したマスタに切り出します。**

`toco-app/data/products.json`

| 項目 | 例 | 出所 |
|---|---|---|
| `id` | `p_evo80` | アプリが採番 |
| `name` | 三晃商会 イージーホーム・エボ80 WH | 楽天API／手入力 |
| `brand` | SANKO(サンコー) | 手入力 |
| `category` | ケージ・サークル | 選択 |
| `image` | `/img/products/p_evo80.jpg` | 楽天APIから取得して保存 |
| `rakuten.itemCode` | `chanet:10181266` | 楽天API |
| `rakuten.url` | `https://item.rakuten.co.jp/...` | 楽天API |
| `amazon.asin` | `B01234ABCD` | **手入力**（商品ページURLから抽出） |
| `yahoo.url` | `https://store.shopping.yahoo.co.jp/...` | 手入力（当面は空欄でよい・§3-7） |
| `specs` | `{外寸: ..., 底面: ...}` | API＋手入力 |
| `reviewSummary` | 高評価／低評価の傾向 | AI分析＋人の確認 |
| `owned` | true / false | **持ちもの台帳と自動照合** |
| `updatedAt` | 2026-09-03 | ― |

**ASINの手入力について**：Amazonの商品ページURLを貼れば、アプリが `/dp/XXXXXXXXXX` の
部分を自動で抜き出します。手作業は「Amazonで商品を探してURLをコピー」だけです。
1商品10秒程度。PA-APIが無くても運用は回ります。

### 3-3. 商品カードの出力

記事の Markdown には、短い記法だけを書きます。

```markdown
### イージーホーム・エボ80 ｜ わが家で使っています

{{product:p_evo80}}

掃除のしやすさで選ぶならこれです。……
```

ビルド時に `{{product:p_evo80}}` が商品カードのHTMLに置き換わります。
出力されるHTMLの構造：

```html
<div class="pd-box" data-product="p_evo80">
  <div class="pd-img"><img src="/img/products/p_evo80.jpg" alt="..." loading="lazy"></div>
  <div class="pd-body">
    <p class="pd-brand">SANKO(サンコー)</p>
    <p class="pd-name">イージーホーム・エボ80 WH</p>
    <div class="pd-btns">
      <a class="pd-btn amazon" href="（テンプレート＋Amazon URL）" rel="nofollow sponsored"
         target="_blank" data-mall="amazon">Amazon</a>
      <a class="pd-btn rakuten" href="..." rel="nofollow sponsored" data-mall="rakuten">楽天市場</a>
      <!-- Yahoo!ボタンは設定で有効化したときだけ出力する（§3-7） -->
    </div>
  </div>
</div>
```

- `rel="nofollow sponsored"` は**必須**。広告リンクであることをGoogleに伝える属性です。
  付いていないとスパム判定のリスクがあります。ポチップは自動で付けています
- デザインは現行ポチップのCSSに寄せます。`https://toco-to.com/wp-content/plugins/pochipp/dist/css/style.css`
  が今も配信されているので、ここから必要な部分を写します

### 3-4. クリック計測

静的サイトでも計測できます。ボタンに `data-mall` を付けておき、
共通JSでクリックを拾ってGA4に送ります。

```javascript
document.addEventListener('click', (e) => {
  const a = e.target.closest('.pd-btn');
  if (!a) return;
  gtag('event', 'affiliate_click', {
    mall: a.dataset.mall,
    product: a.closest('[data-product]').dataset.product,
    page: location.pathname,
  });
});
```

ポチップの計測より、むしろ細かく取れます（どの記事のどの商品か分かる）。

### 3-5. 画像の扱いと規約 ★

商品画像は規約が厳しい領域です。

| 出所 | 使えるか | 条件 |
|---|---|---|
| 楽天APIの画像 | **使える** | 楽天へのアフィリエイトリンクとセットで使う |
| Amazonの画像 | **PA-API経由でのみ** | 直リンク・保存はNG。PA-API未取得の間は使わない |
| Yahoo!の画像 | 使える | バリューコマースの規約に従う |

**フェーズ1の方針：商品画像は楽天APIのものを使う。**
楽天に無い商品（Amazon限定品など）は画像なしのカードにする、
またはその商品を採用しない、で運用します。

なお楽天の画像はホットリンク（楽天のサーバーを直接参照）も可能ですが、
表示速度と安定性のため**ビルド時にダウンロードして自サイトに置きます**。
`sips`（macOS標準）でリサイズとWebP変換をかけます。追加ソフトは不要です。

### 3-6. 価格を出さない設計

静的サイトは、ビルドした瞬間の状態で固まります。価格を書き込むと、
値上げされた翌日から嘘を掲載していることになります。景品表示法の観点でも危険です。

- 本文にもカードにも価格を書かない（CLAUDE.md で既に決定済み）
- カードの下に「価格は変動します。最新の価格は各ストアでご確認ください。」を自動で入れる
- 比較表の判断軸は価格ではなく、サイズ・素材・掃除方式・向いている人にする

**この方針が、ポチップの唯一の再現できない機能を無効化します。**
制約ではなく、静的サイトに合わせた設計判断です。

### 3-7. Yahoo!ボタンは当面出さない（決定）

商品カードのボタンは **Amazon・楽天の2つ**にします。

**出さない理由**

| 論点 | 内容 |
|---|---|
| 報酬率 | Yahoo!が3モールで最も低い。Amazonで買うはずの人がYahoo!に流れると単価が下がる |
| スマホの押しやすさ | 2等分のほうが1ボタンの幅が広く、押しやすい |
| 運用の手間 | 商品ごとにYahoo!のURLを探す時間が増える。**月10本を維持することのほうが収益に効く** |
| 提携の手間 | もしもでYahoo!を扱えるかの確認、扱えなければバリューコマースの登録と審査が要る |

**捨てているもの**：Yahoo!／PayPay経済圏の読者の取りこぼし。全クリックの5〜10%程度。

**後から足せるようにしておく**

- 商品マスタには `yahoo.url` の欄を**最初から用意**する（空欄のまま運用）
- 設定画面に「Yahoo!ボタンを表示する」チェックボックスを置く
- チェックを入れると、次回ビルドから全記事の全カードに3つ目のボタンが出る

**見直しのタイミング**：記事30本を超えてGA4にクリックデータが溜まったら、
Amazonと楽天のクリック比率を見て判断します。楽天が極端に多い場合は
モール志向の読者が多いということなので、Yahoo!を足す価値があります。

## 4. 静的サイト生成の設計

### 4-1. 出力するもの

| パス | 内容 | 生成元 |
|---|---|---|
| `/` | トップ | `front-page` テンプレート＋記事一覧 |
| `/{slug}/` | 記事 | `articles/*.md` |
| `/category/{cat}/` | カテゴリ一覧（ページ送りつき） | 記事のメタ情報 |
| `/tag/{tag}/` | タグ一覧 | 同上 |
| `/beginner/` `/contact/` `/privacy/` `/about/` | 固定ページ | `pages/*.md` |
| `/archive/` `/ranking-top20/` | 既存の固定ページ | 移植 |
| `/404.html` | 404 | 監査A-2の指摘を直した内容にする |
| `/sitemap.xml` | サイトマップ | 自動 |
| `/feed.xml` | RSS | 自動 |
| `/robots.txt` | クロール設定 | 自動 |
| `/search-index.json` | サイト内検索用 | 自動 |
| `/img/...` `/assets/...` | 画像・CSS・JS | ― |

### 4-2. URL設計

- 記事は **`/{slug}/`** のフラット構造にします（例：`/rabbit-cage/`）
  - カテゴリを後から変えてもURLが変わらないため
  - 旧サイトの `/1534` 形式は公開記事が0本なので引き継ぎ不要
- 末尾スラッシュあり、`index.html` を各ディレクトリに出力
- 旧記事URL（`/1534` 等）へのアクセスは、Cloudflareのリダイレクトルールで
  トップに301しておきます（数行の設定で済み、404を減らせます）

### 4-3. WordPress／プラグイン機能の置き換え

### 5-3. デプロイ経路

**GitHub連携方式を採ります（アカウントあり・決定）。**

```

  → git add / commit / push
  → Cloudflare Pages が push を検知して自動デプロイ
```

理由：

- 記事とサイトの**バックアップが自動で取れる**（Macが壊れても失われない）

- Cloudflare側で「デプロイのやり直し」ができる
- `git` は macOS に標準で入っているので、追加インストール不要

GitHubは**プライベートリポジトリ**にします（下書きも入るため）。

### 5-4. お問い合わせフォーム

現状 `/contact/` は404です（監査A-1）。静的サイトではPHPが動かないので、
Cloudflare Pages Functions という仕組みを使います。

```
functions/api/contact.js   ← このファイルを置くだけで
                              https://toco-to.com/api/contact が動く
```

中身は「フォームの内容を受け取って、指定のメールアドレスに転送する」だけの短いコードです。
スパム対策には Turnstile（Cloudflare製・利用者は何も操作しなくてよい）を入れます。

**もっと簡単な代替**：Googleフォームを埋め込む方法もあります。実装ゼロで済みますが、
デザインが揃わないのと、フォームがGoogleのドメインになる点が引っかかります。
まずはPages Functionsで作り、詰まったらGoogleフォームに退避、という順で進めます。

| # | 確認 | 理由 |
|---|---|---|
| 1 | ASP・Google・Amazon等の登録メールアドレスが `@toco-to.com` になっていないか | なっていると連絡が届かなくなる |

移管のメリットは更新料が原価（年1,500円前後）になることと、
更新忘れが起きにくいことです。急ぐ理由ではありません。

## 13. フェーズ3の記録（2026-09-03 完了）― アプリの作り替えと公開機能

### やったこと

WordPressへの投稿をやめ、**アプリから直接サイトを公開できる**ようにしました。
あわせて 1,397行の `server.js` を役割ごとに分割し、画面を組み直しています。

### ファイル構成

```
toco-app/
  server.js            531行。受付（ルーティング）だけ
  lib/
    db.js              設定・記事ネタ・持ちもの台帳
    articles.js   ★新  記事ファイル（articles/*.md）の読み書き
    research.js        楽天の商品検索・レビュー取得
    brief.js           執筆用の材料
    claude.js          Claude Code の呼び出し
    checks.js          公開前チェック
    markdown.js        Markdown → HTML
    site-config.js     サイト名・カテゴリ・メニュー
    build.js           サイトの書き出し
    deploy.js     ★新  Git で公開する
    preview-server.js  dist/ をローカル配信（ポート4569）
  public/              画面（index.html / style.css / app.js）
  site/                テンプレート・アイキャッチ・ファビコン
  data/
    db.json            記事ネタ・持ちもの台帳・作業記録（Gitに入れる＝バックアップされる）
    secrets.json  ★新  APIの鍵だけ（.gitignore で除外）
```

**鍵と作業データを分けた**のが要点です。`data/` を丸ごと除外すると持ちもの台帳や
記事ネタがバックアップされないため、鍵だけを `secrets.json` に切り出しました。

### 記事の持ち方を変えた

| 変更前 | 変更後 |
|---|---|
| 本文が `db.json` の `projects[].article` に入っていた | `articles/{スラッグ}.md` が正 |
| メタ情報がWordPress側にあった | Markdownのフロントマターに持つ |

理由は2つ。**120本ぶんの本文をJSONに抱えると読み書きが重くなる**こと、
**1記事1ファイルならGitの差分で「どこを直したか」が読める**ことです。

### 画面

| 画面 | 内容 |
|---|---|
| ホーム | サイトの状態・未反映の変更・作業中の記事・気づきメモの入力 |
| 記事ネタ | キーワード一覧（絞り込み・優先度） |
| 記事 | 一覧 → 詳細（**4ステップ**：商品を選ぶ／本文を書く／公開前チェック／公開の設定） |
| 持ちもの台帳 | 使用中の用品と日付つきメモ |
| **公開** | ビルド・反映・記事ごとの公開切替・履歴・初期セットアップ |
| 設定 | 楽天API・Claude・IP確認 |

画面の位置はURLに残します（`#publish`、`#edit/<id>/4`）。ブラウザの戻るが効きます。

### 公開の流れ

```
①ビルド    dist/ にサイト一式を書き出す
②コミット  変更をGitに記録する（間違えても戻せる）
③プッシュ  GitHubに送る
④デプロイ  Cloudflare Pages が自動で公開（1〜2分）
```

①〜③をアプリの「サイトに反映する」1ボタンで実行します。

**安全装置**：`data/` が `.gitignore` に入っていない状態では、
プッシュを実行せずに中止します（鍵が公開されるのを防ぐため）。

### 動作確認（実施済み）

| 確認 | 結果 |
|---|---|
| 記事のフロントマター読み書き | 正常 |
| 4ステップの画面遷移・URL連動 | 正常 |
| ビルド → コミット | **96ファイルを記録。0.3秒** |
| `data/` の除外 | **追跡0件**（鍵は記録されていない） |
| プッシュ | GitHub未設定のため実行せず（想定どおり中止） |

### 残っていること

1. GitHubでプライベートリポジトリを作り、アプリの「公開の準備」にURLを貼る
2. Cloudflare Pages でそのリポジトリを選び、**出力先を `toco-app/dist`、ビルドコマンドは空**にする
   （画像処理に macOS の `sips` を使うため、Cloudflare側ではビルドしません）
3. フェーズ2（アフィリエイト）— もしものリンク2本が届き次第
